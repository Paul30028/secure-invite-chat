# 项目接手计划

## 当前定位

本仓库是可运行的端到端加密聊天原型，不应在现阶段被描述为 Signal 等级的安全通信产品。后续工作以“先建立可信安全边界，再扩展功能”为原则。

## 不变量

- 服务端不得持有聊天、文件或通话媒体的解密密钥。
- 服务端不得把客户端提交的 `device_id` 当作已认证身份。
- 生产客户端不得将私钥、群密钥或管理员凭证保存在 `localStorage`。
- 公网环境必须使用 `wss://`；推送内容不得包含聊天明文。
- 成员被移除后，新消息必须使用新的群密钥 epoch。

## 阶段 A：安全底座

1. 定义版本化认证握手：服务端 nonce、设备签名、短时会话与连接绑定身份。
2. 将身份密钥、群密钥和管理员凭证迁移到各平台安全存储；Web 仅作为受限开发目标。
3. 对协议实行严格 schema、大小限制、速率限制、分页历史和可观测审计。
4. 验签失败、身份不匹配或重放消息必须被拒绝，不能以普通消息形式展示。

## 阶段 B：私密消息与文件

1. 一对一会话采用经独立安全评估的双棘轮实现。
2. 群组改用支持成员变更的 epoch 密钥体系；评估 MLS 实现及许可证。
3. 文件按块客户端加密，服务端只保存密文对象、完整性哈希和过期策略。
4. 链接预览默认本地生成；任何代理抓取必须由用户显式选择。

## 阶段 C：音视频与公开通知

1. 一对一通话采用 WebRTC；群通话使用 SFU 转发和编码帧端到端加密（见 `CALLS_MEDIA_ARCHITECTURE.md`）。
2. TURN/SFU、推送与投递服务的元数据最小化单独建模与披露。
3. 首页公开通知采用发布者签名、客户端验签；它与私密聊天密钥体系完全隔离（见 `PUBLIC_NOTICES_PROTOCOL.md`）。

## 发布门槛

- 每次提交执行前端构建、Python 编译检查与自动化测试。
- 为认证、消息验签、成员移除、密钥轮换和文件分块建立互操作测试向量。
- 完成第三方密码学审计、渗透测试、依赖审计和发布包签名后，才考虑公开生产部署。
