# 首页公众通知协议（设计稿）

> 状态：尚未实现。此模块用于发布可公开传播的通知，不属于私聊系统，也不继承私聊的身份、密钥或可见性。

## 目标

- 客户端只显示经过可信发布者签名的公告。
- 不要求读者注册、登录、加入群或暴露私聊设备标识。
- 推送和拉取都不携带私聊明文、群 ID、联系人或群成员关系。
- 支持公告撤回、更正、过期与密钥轮换，并允许离线验证。

## 非目标

- 公告内容默认是公开的；签名证明来源与完整性，**不提供保密性**。
- 不把“订阅了某频道”伪装为匿名：网络服务商、CDN 或推送服务仍可能观察请求时间与 IP。
- 不借公告服务绕过私聊的成员权限、消息投递或文件传输限制。
- 不在公告客户端中执行远端 HTML、脚本、像素追踪或自动链接预览。

## 身份与信任根

每个发布频道有稳定的 `publisherId` 和 Ed25519 公钥。客户端使用渠道目录（manifest）建立信任，而不是首次看到公钥就信任：

```json
{
  "version": 1,
  "publisherId": "org.example.status",
  "displayName": "示例服务状态",
  "keyId": "2026-q3",
  "publicKey": "<base64url Ed25519 SPKI 或协议固定编码>",
  "previousKeyId": "2026-q2",
  "validFrom": "2026-07-01T00:00:00Z",
  "manifestSignature": "<由内置根或旧密钥签名>"
}
```

- 初始可信频道目录随应用签名发布；普通内容服务不能自行添加可信发布者。
- 新密钥须由当前可信旧密钥签名，并限定生效时间；根密钥变更须经应用更新或独立透明日志确认。
- 不使用私聊设备 P-256 身份键签公告。发布系统另有专用签名键，泄露影响范围更小。

## 公告信封

签名使用规范化二进制编码（CBOR/Protobuf 的确定性编码），不能对 JSON 字符串直接签名。签名输入固定为下列字段，按字段号和长度编码：

```text
version | publisherId | keyId | noticeId | sequence | issuedAt | expiresAt |
kind | title | body | attachments | replaces | revokes
```

```json
{
  "version": 1,
  "publisherId": "org.example.status",
  "keyId": "2026-q3",
  "noticeId": "018f4df1-…",
  "sequence": 1042,
  "issuedAt": "2026-07-20T10:00:00Z",
  "expiresAt": "2026-08-20T10:00:00Z",
  "kind": "notice",
  "title": "服务维护通知",
  "body": "……",
  "attachments": [],
  "replaces": null,
  "revokes": [],
  "signature": "<base64url Ed25519 signature>"
}
```

字段限制：

- `noticeId` 为 UUIDv7 或 128 位安全随机值；同一 ID 内容不可变。
- `sequence` 对每个发布者严格递增，用于发现回滚与重放。
- `issuedAt` 和 `expiresAt` 是展示/缓存策略，不能单独作为可信时间；允许合理时钟偏差。
- 标题、正文和附件元数据均进入签名。附件只能引用内容寻址的密文或公开静态对象，并携带 hash、字节数和 MIME 白名单。
- `kind: "revoke"` 只撤回指定 ID；撤回记录本身永久保留在客户端历史中，避免旧镜像重新显示失效公告。

## 客户端验证与显示

1. 校验 schema、版本、大小、UTF-8 与字段长度。
2. 从已信任目录取得 `publisherId + keyId`，验证密钥有效期与轮换链。
3. 用确定性编码重建签名输入；验签失败、未知发布者、过期密钥或 sequence 回退一律隔离，不渲染正文。
4. 存储最近已验证的每频道最大 sequence、公告 ID 和撤回集合；重复内容幂等处理。
5. 只把通过验证后的纯文本/受限 Markdown 交给 UI。外链需用户点击才打开，并显示目标域名；不自动下载附件。
6. UI 明确标注“公开公告”，不得与端到端私聊消息使用相同视觉标签。

## 拉取、缓存与推送

```
客户端 ──匿名/最小化 GET──> 公告 CDN/API ──> 签名公告批次
客户端 <──仅不透明唤醒──── 推送服务 <────── 公告服务
```

- 同一请求只含频道 ID、cursor 和协议版本；不含私聊设备 ID、群 ID、通讯录或登录 token。
- cursor 是与频道绑定的随机同步令牌，不能跨频道关联；服务端只保留短期聚合指标。
- 推送 payload 仅含 `publisherId`、可能的版本/刷新提示和随机通知 ID；正文、标题、链接、群信息均不进入推送。
- 客户端收到唤醒后自行拉取与验签；离线时显示已验证的缓存，并标明缓存时间。
- 若产品需要反审查/多镜像，镜像只提供字节分发；安全性仍由签名、回滚检测和透明日志保障，而非镜像自身信誉。

## 服务端边界

公告服务保存发布者签名后的不可变记录，不能替客户端签名、改写正文或将公告请求与私聊投递数据库关联。发布后台采用独立账户、独立密钥和独立审计日志；发布权限不授予聊天管理员 token。

建议 API：

- `GET /v1/notices/{publisherId}?cursor=…`：返回签名原件和下一 cursor。
- `GET /v1/publishers/{publisherId}/manifest`：返回签名目录项/轮换链。
- `POST /v1/admin/notices`：仅发布后台，要求硬件/离线签名结果；API 不持有在线签名私钥。
- `GET /v1/transparency/{publisherId}`：可验证的追加日志检查点与包含证明。

## 发布门槛

在下列条件满足前，不在首页启用真实公告源：

- 确定性编码、Ed25519 验签、key rotation、revoke 与回滚检测具备测试向量。
- 发布私钥在离线或硬件保护环境中；线上 API 不可导出或代签。
- 客户端验证失败的 UI 隔离、缓存清理和深链打开规则通过安全测试。
- 接口、CDN、推送和分析均完成元数据评估，且隐私政策如实披露剩余暴露面。
